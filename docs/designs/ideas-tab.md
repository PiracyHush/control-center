# Design: Ideas tab, where ideas grow while you work

Generated by /office-hours on 2026-10-17
Branch: codex/project-routing
Repo: PiracyHush/control-center
Status: APPROVED
Mode: Builder

## Problem Statement

Ideas that come up while working on one project (Proof of Work, MetaMarket/Market Scout, Climate Discount, the Kinematics study) get lost because writing them down means leaving the work in front of you. When they are written down, they sit untouched in chats, notes and research folders and never grow. The Control Center dashboard needs an Ideas tab where ideas are captured without breaking flow and keep growing afterwards: picking up notes, evidence and connections to each other, to projects and to the stories the dashboard already collects.

## What Makes This Cool

- **Ideas grow while you are not looking.** The coding agents you already work with file side ideas and add notes to existing ones as part of the handoff report they send at the end of every session. Capture and growth are a by-product of work you were doing anyway.
- **Ideas connect.** An on-demand Connect job suggests links between ideas and to recent stories, with a reason for each; you accept or reject.
- **It is built on pipes that already exist.** Handoff reports, project routing, the acceptance ledger, the weekly review and the OpenAI provider are all in place. The Ideas tab mostly connects them.

## Constraints

- Local-first Next.js 16 app, SQLite in the data directory, loopback only, no login. Fail-closed storage and the `proxy.ts` boundary stay as they are.
- 8 GB laptop: no background AI loops; AI runs on demand or as a capped batch.
- At most 8 configured projects (existing project-routing limit).
- New AI use must be opt-in, and documented as an exception to the current promise in `SECURITY.md` that task, reminder and private content is never sent to a provider.
- Handoff schema v1 is already used by two repositories, so changes must be backward compatible.

## Premises

1. **Ideas are not tasks.** The Ideas tab is separate from Tasks; an idea becomes tasks or a project only when you promote it.
2. **Capture rides the handoff pipe.** Agents add ideas and notes through the existing handoff report; you can also add ideas by hand in the tab.
3. **New ideas need your yes; notes do not.** A new idea from an agent arrives as a proposal you keep or dismiss. Notes on ideas you already kept attach automatically, labelled as written by an agent from a named project session.
4. **Growth is visible.** Each idea shows its origin (project, session) and a timeline of notes, and can link to other ideas and to projects.
5. **AI is allowed, opt-in (revised in session).** With an Ideas AI setting turned on, the dashboard may send idea text (including agent-written notes) and recent story headlines to the selected provider (OpenAI today) to summarise ideas and suggest links. Clusters are computed locally from accepted links, not by AI. Off by default; nothing is sent while it is off.
6. **A graveyard guard.** Growing ideas untouched for 21 days appear in the weekly review and the tab's "Needs a look" list, with Keep, Park or Drop.

## Approaches Considered

### Approach A: Minimal (capture and grow)
Ideas tab with quick-add, handoff `ideas` and `ideaNotes`, notes timeline, on-demand AI summary. No links between ideas. Ruled out: delivers growth but not the connections you asked for.

### Approach B: Full (capture, grow and connect), chosen
Everything in A plus idea-to-idea and idea-to-story links, a batched AI Connect job whose suggestions you accept or reject, an idea map, the graveyard guard, and promotion to tasks or a project.

### Approach C: Ideas as Markdown files in the knowledge base
Ruled out: splits data between files and the dashboard, needs cross-repo write access, and weakens the keep-or-dismiss step for new ideas.

## Recommended Approach

Approach B. You chose "It grew and connected" as what should happen to an idea and "Agents grow it" as the growth you would miss most; B is the only option that delivers both, and it reuses the handoff pipeline instead of adding a new one.

### Data model (SQLite, additive tables initialised idempotently like the handoff tables)

| Table | Columns | Notes |
| --- | --- | --- |
| `ideas` | id (dashboard id, e.g. `idea_<uuid>`), title, status (`proposed`, `growing`, `parked`, `dismissed`, `dropped`, `promoted`), origin_kind (`manual`, `agent`), origin_project_id, origin_report_id, origin_key, summary, summary_at, promoted_to, created_at, last_grown_at, last_reviewed_at | see rules below |
| `idea_notes` | id, idea_id, body, author (`you`, `agent`, `connect`), project_id, report_id, created_at | append-only timeline; adding a note updates `last_grown_at` |
| `idea_links` | id, idea_id, target_kind (`idea`, `story`, `project`), target_id, target_title, target_url, status (`suggested`, `accepted`, `rejected`), reason, source (`you`, `connect`), created_at | see rules below |
| `ideas_meta` | key, value | holds `connect_last_run_at`, so the hourly limit survives restarts |

Rules:

- **Agent dedupe.** `origin_key` holds the agent-supplied idea id from a handoff; manual ideas leave it null. A unique index on `(origin_project_id, origin_key)` (where `origin_key` is not null) means re-importing a report never duplicates an idea.
- **Dismiss** sets status `dismissed` and keeps the row, so the dedupe index also stops the same proposal coming back. **Drop** (from Needs a look or the idea view) sets `dropped`.
- **Promotion.** `promoted_to` is JSON: `{"kind":"tasks","taskIds":[...]}` or `{"kind":"project","projectId":"..."}`; status becomes `promoted`. Tasks created from an idea get a new optional `ideaId` field on `TaskItem`, validated in `cleanTaskItems` (additive, like the existing focus fields), which is the back-link. Promote to project adds a project-routing entry and is refused with a clear message when the 8-project cap is full.
- **Cap.** At most 500 ideas count toward the limit: statuses `proposed`, `growing` and `parked`. Dismissed, dropped and promoted ideas do not count. At the cap, quick-add is refused with a message; a handoff import still imports the report but skips its new ideas and returns `ideasSkipped: N`, shown in Updates.
- **Links.** Idea-to-idea links are stored as an unordered pair (smaller id in `idea_id`) with a unique index on `(idea_id, target_kind, target_id)`, so a rejected A-B pair also blocks B-A. Story links store the headline and URL at link time, so they still display if the story is later pruned from the feed.
- **Untouched** means `max(last_grown_at, last_reviewed_at)` is older than 21 days, for `growing` ideas only (parked ideas are deliberately set aside). **Keep** sets `last_reviewed_at` to now.
- **Bounds:** title 200 chars, note 2,000 chars, link reason 300 chars.

### Handoff extension (schema v1, backward compatible)

Two optional arrays in the report, validated by `parseHandoff` in `lib/project-handoffs.ts` and produced by `scripts/export-handoff.mjs`:

- `ideas: [{ id, title, note? }]` creates `proposed` ideas, with `id` stored as `origin_key`, so re-imports never duplicate them.
- `ideaNotes: [{ ideaId, body }]` appends agent notes. `ideaId` is always the **dashboard** id (`idea_<uuid>`), never the agent's own id, so an agent in any project can add to any growing or parked idea, including ones you created by hand. Notes for unknown, proposed, dismissed, dropped or promoted ideas are ignored and counted in the import result.

**How an agent learns the dashboard ids.** `npm run handoff:export -- --list-ideas` (run in a project repo) fetches `GET http://127.0.0.1:3000/api/ideas?status=growing,parked` over loopback, which passes the existing `proxy.ts` host check and sends no Origin header. It prints id and title for each idea. It never reads the dashboard's SQLite file directly. If the dashboard is not running, or the request fails, it prints "Dashboard not reachable: idea list unavailable" and the export still works; the agent can propose new ideas but cannot add notes in that session.

The project repos' agent instructions (AGENTS.md in Proof of Work and MetaMarket) gain one paragraph: list ideas at the start of a session, then record side ideas and notes in the handoff. This is a one-time manual doc change made in each repo's own session, not something the dashboard writes into other repos.

### Untrusted input

Idea titles and notes written by agents in other repositories are untrusted.

- **In the UI:** rendered as plain text through React's default escaping, with no Markdown or HTML rendering.
- **In AI prompts:** idea content is placed inside a clearly delimited data block, with an instruction to treat it as data and ignore any instructions inside it. Model output is accepted only as a list of `{ ideaId, targetKind, targetId, reason }` whose ids were in the request, with the reason capped at 300 chars.
- **Disclosure:** `SECURITY.md` states that when the Ideas AI setting is on, agent-written notes, which may describe private project work, are part of what is sent.

### AI (opt-in, `Settings > Ideas > Use AI for ideas`)

- **Summarise:** per idea, on demand. Sends that idea's title and notes; stores a summary and its timestamp.
- **Connect:** manual "Run now", limited to once an hour (last run time stored in `ideas_meta`). Sends the 50 most recently grown `growing` ideas and at most 40 story headlines from the last 7 days. Each idea is sent as its title plus its summary if one exists, otherwise its latest notes truncated to 300 characters in total. Returns suggested links with a reason. Only ids that were sent are accepted, suggestions land as `suggested`, and rejected pairs (unordered for idea pairs) are never re-suggested. It uses the existing provider code in `lib/server/ai.ts`; failures show an error and change nothing.
- **Clusters** on the map are the connected groups of accepted idea-to-idea links, computed locally. No AI call is involved.
- `README.md` and `SECURITY.md` state exactly what is sent, when, and that it is off by default.

### UI (approved wireframe: list, idea with timeline, connections)

- **Left:** quick-add, "waiting for you" proposals with Keep and Dismiss, then the idea list with origin project, note count and last-grown age.
- **Middle:** the selected idea with its AI summary (and a Summarise button), a timeline labelled by author, add note, Promote to tasks, Promote to project, Park.
- **Right:** idea map (accepted links, clustered), linked items, Connect suggestions with Link or Not related, and "Needs a look" for ideas untouched for 21 days.
- **Elsewhere:** a new Ideas nav tab and app shortcut; the Updates report view lists a report's new ideas and notes; the weekly review gains an "Ideas untouched 21+ days" line.

## Success Criteria

Two weeks after shipping:
- At least 10 ideas captured, at least half of them by agents through handoffs.
- At least 3 ideas with notes from two or more different sessions (real growth, not one-off capture).
- At least 30% of Connect suggestions accepted. Lower means the prompt or inputs need work.
- At least 1 idea promoted to tasks or a project.
- No idea text leaves the machine while the AI setting is off (verified by a test that stubs the provider).

## Next Steps: routed workflow plan

Routing rules applied by hand from `reports/model-router-architecture.md` (the `route` skill is designed but not built). Tiers map to what exists today:

- **Low:** `scout` (Haiku), read-only exploration.
- **Mid:** `builder` (Sonnet), implementation and tests.
- **Top:** the main session (Opus) for implementation, because the `architect` agent is a read-only reviewer that cannot edit; `architect` is used only for review steps.

A step touching `lib/server/database.ts`, storage, task or project data, the handoff parser, AI calls or `SECURITY.md` goes up one tier and is never downgraded. Writers run one at a time; reads may run in parallel between writes. Each step has an allowlisted check, and failed steps are rolled back without touching anything else:

- **Snapshot before each write step.** With a throwaway index file (`GIT_INDEX_FILE=<temp file>`), run `git add -A` then `git write-tree`. This captures every tracked and untracked, non-ignored file as a tree without changing HEAD, the real index or your staged work. The tree id is written to the run log next to the step id.
- **What changed.** After the step, take a second snapshot the same way and list changed paths with `git diff --no-renames --name-status <before> <after>`, so every change is reported as M, D, A or T and never as a rename. T (type change) is restored like M. Any other status stops the run without retrying.
- **Restore on a failed check.** Split the changed paths:
  - Paths that existed in the before snapshot (status M or D): restore them with `git restore --source=<before> --worktree -- <those paths>`.
  - Paths the step created (status A): delete exactly those files.
  - Never `reset --hard` or `git clean`. Ignored files such as `node_modules` and `.env*` are outside this guarantee.
- **Retry** one tier up, once, from the restored tree. A second failure stops the run and reports the before-snapshot id of the run's first step, so the whole run can be undone the same way.

### R3-1 — feasibility (blocking)

**Problem**

> `git diff` enables rename detection by default (diff.renames=true since Git 2.9), so a step that moves or substantially rewrites a file into a new path reports it as `R<score> old new` (and type changes as `T`), not as D plus A. The restore rule only handles M, D and A, so on a failed check a renamed file's old path is never restored and its new path is never deleted, leaving the retry to start from a partially changed tree, which is exactly what the rollback promises to prevent.

**Remedy**

> Run the diff with `--no-renames` (so every change is M, D, A or T) and state how any other status (T, or an unexpected one) is handled, e.g. treat T like M and stop the run on anything else.

### R3-2 — completeness (minor)

**Problem**

> It is not stated whether the failed retry's own changes are restored before the run stops, so the tree may be left in the retry's failed state. The whole-run undo against the first step's before-snapshot would also revert any edits the user made by hand while the run was going.

**Remedy**

> State that the failed retry is restored with the same split rule before stopping, and warn that a whole-run undo also reverts manual edits made during the run.

### R3-3 — clarity (minor)

**Problem**

> If the temp file is pre-created as a 0-byte file (as mktemp does), Git rejects it as a corrupt index. Deleting created files also leaves their now-empty directories (e.g. `app/api/ideas/`). Changes a step makes to HEAD or the real index (a commit or `git add`) are not undone by a worktree-only restore.

**Remedy**

> Use a non-existent temp path (or delete the file first), remove empty directories left after deleting created files, and state that write steps must not commit or stage.

### R3-4 — clarity (minor)

**Problem**

> A project-routing entry needs an id, a name and keywords; the design does not say how these are derived from the idea on Promote to project or how an id collision with an existing project is handled.

**Remedy**

> State how the new ProjectRoute's id, name and keywords are filled on promotion and what happens on an id collision.

### R3-5 — consistency (minor)

**Problem**

> Open Questions still asks what happens when Promote to project hits the 8-project cap, but the Promotion rule already decides it (refused with a clear message).

**Remedy**

> Remove the cap question from Open Questions or mark it decided.

### R3-6 — feasibility (minor)

**Problem**

> `--list-ideas` still hardcodes http://127.0.0.1:3000 although the dashboard port is configurable, so it reports the dashboard unreachable when it runs on another port.

**Remedy**

> Let `--list-ideas` take a URL or port argument, defaulting to http://127.0.0.1:3000.

### R3-7 — clarity (minor)

**Problem**

> Summaries have no staleness indication: after new notes arrive, the stored summary (and the Connect input that prefers it over notes) can be out of date.

**Remedy**

> Mark a summary as out of date when `summary_at` is older than `last_grown_at`, and consider sending notes instead of a stale summary to Connect.

**Remedy**
